# LMS demo console

The same console built twice, against one API, plus the API reference.

| Path | What |
|---|---|
| `angular/` | Angular 22: standalone components, signals, hash routing |
| `react/` | React 19 + Vite, hooks, React Router |
| `swagger/`, `landing/` | Swagger UI and the landing page |
| `build-site.sh` | Builds all of it into `site/`, laid out as it is published |
| `e2e/` | Playwright browser tests, run against both consoles and a real backend |

Published to GitHub Pages by `.github/workflows/pages.yml` at
`/<repo>/angular/`, `/<repo>/react/` and `/<repo>/api/`.

## The API clients are generated

Neither app has a hand-written API client. Both are generated by
[OpenAPI Generator](https://openapi-generator.tech) from the assembled contract
(`typescript-angular` and `typescript-fetch`), into `src/app/api` and
`src/api`, which are not committed. `npm run build` and `npm start` / `npm run dev`
regenerate them first.

```
(cd backend && ./mvnw -q generate-sources)   # writes backend/target/openapi/openapi.yaml
cd frontend && ./build-site.sh               # or: cd angular && npm install && npm start
```

## The adapter

Screens never import the generated client. They depend on `LmsGateway`
(`gateway/lms-gateway.ts`, `gateway/lmsGateway.ts`): a small interface of
display-ready types. One adapter per app (`generated-lms-gateway.ts`,
`generatedGateway.ts`) turns the generated client into it, defaulting the
contract's optional fields and normalising errors to `ApiProblem`. A contract
change can only break the adapter, and a fake gateway is enough to test a screen.

## Pointing at another backend

Angular reads `<meta name="lms-api-url">` from its `index.html` at run time
(`angular/src/app/config.ts`), so one build serves any backend; React reads
`VITE_API_URL` at build time. `build-site.sh` sets both from `API_URL`.
The backend must list the Pages origin in `CORS_ALLOWED_ORIGINS`.

Demo only: the access token is held in memory and is gone on reload.

## Delivery, claims, print and QR codes

The sidebar's **Delivery** section holds **Claims** (raise, review, approve or
reject, settle) and the **Delivery desk** (issue the consignee's one-time code,
record the proof). Controls appear only for callers who hold the permission:
`CLAIM_READ`, `CLAIM_RAISE`, `CLAIM_DECIDE`, `POD_READ`, `POD_RECORD`.

A claim and a proof of delivery each have a slip. **Print slip** shows it, and
**Print** opens the browser's print dialog; `src/print.css` makes the slip the
only thing on the printed page. The slip's QR code (`LMS:CLAIM:<claim number>`,
`LMS:CONSIGNMENT:<consignment id>`) is drawn in the browser by the `qrcode`
package from text the page already holds. Nothing is rendered or stored by the
backend, so printing adds no load to it.

## Tracking links

**Delivery > Tracking links** (permission `TRACKING_LINK_MANAGE`) issues, lists
and revokes the links a customer follows a consignment by. A link's secret is
shown once, when it is issued, with a Copy button and a printable slip whose QR
code is the link itself (drawn in the browser, like the other slips). The link
opens **Track your shipment** (`#/track/<token>`), a page that needs no
sign-in and shows only what the public endpoint returns; an unknown, expired
and revoked link all show the same message. The public read is made with no
credentials, even from a console that is signed in.

## Demo data

**Settings > Demo data** (permission `DEMO_RESET`, on a deployment with the
demo switched on) puts the demo tenant back to its seeded state: everything in
it is deleted and its administrator is created again with the same password.
It asks once before it does anything. The administrator's user is recreated,
so the screen then offers to sign in again. The backend can also do this on a
timer (`DEMO_RESET_CRON`).

## Allocation rules

**Operations > Allocation rules** (read with `ALLOCATION_RULE_READ`, write with
`ALLOCATION_RULE_MANAGE`) lists the rules in the order they are tried, writes
and edits them (conditions: origin, destination, weight band, goods; action:
PREFER its vendors in the order added, or EXCLUDE them) and retires or
reinstates them -- a rule is never deleted. A **dry run** takes a load id and
shows which rule would fire and who would be asked first, without offering
anything; **What decided an allocation** takes an allocation id and names the
rule that fired on it. Validation is the API's: its message is shown as given.

## Maps

**Operations > Network map** draws every site with its geofence and every
vehicle at its last reported position; **Operations > Trip route** draws a
trip's reported track and where it is now; **Multimodal > Itineraries** draws
an itinerary's legs between their terminals (rail dashed, road solid) and
**Multimodal > Milk runs** a route's circuit from the plant round its stops and
back. Everything drawn comes from the existing read APIs; nothing is computed
on a server for the map.

Maps use [Leaflet](https://leafletjs.com) (BSD-2-Clause), loaded only when a map
screen is first opened. Tiles come from the public OpenStreetMap servers by
default, which allow light use only. Point a deployment at its own tiles with
`<meta name="lms-tile-url" content="https://.../{z}/{x}/{y}.png">` (and
`lms-tile-attribution` for the credit) in either console's `index.html`;
React also reads `VITE_TILE_URL` at build time. Under each map the same
features are listed as text, with their kind and coordinates on `data-`
attributes, for screen readers and for the browser tests, which answer tile
requests themselves and never call the tile servers.

## Client-side cache

Both consoles keep what the maps need in the browser so the 0.1-CPU backend is
asked for less (DOCS/adr/0007). Each has a small `client-cache` module over the
native IndexedDB API (no library): a database per tenant and user, entries with
a TTL and a version, `get`/`put`, a wipe on sign-out, and a wipe when `GET /me`
returns a different `cacheEpoch`. It is bound at sign-in and does nothing when
the `ui.clientCache` setting is off.

- **Geometry.** Terminals (network map, itineraries, milk runs) are kept and
  revalidated with `If-None-Match`: 5 minutes with no request, then a `304`.
- **Tracks.** Trip route keeps the points and asks `track?afterSeq=` for the
  rest; a track over 1500 points is simplified (Douglas-Peucker) in a Web Worker
  before it is drawn. The exception desk's severity and status counts are also
  worked out in that worker, from the tickets already listed.
- **Tiles.** `tile-sw.js` is a service worker, registered in production builds
  only and scoped to the console's path. It caches tile images in the Cache API
  (cache first, 7 days, 600 tiles, least recently used out first) and ignores
  everything else, so it never holds an API response.

Angular keeps the workers as `src/app/workers/*.worker.ts` (built by
`webWorkerTsConfig`); React imports them with `new URL(..., import.meta.url)`.
`tile-sw.js` is copied as is: from `src/` in Angular, from `public/` in React.
The browser tests block service workers, because Playwright cannot route what a
worker fetches. There is no unit-test runner in either console; the cache is
covered by `client-cache.spec.ts`.

## LTL rating and parked events

**Finance > LTL rating** lists the receivable each part-load docket earned
(`INVOICE_READ`) and, for `TARIFF_MANAGE`, puts a site in a zone and publishes a
zone-to-zone rate card. Zones and rate cards have no list endpoint yet, so they
are written here and seen through the receivables they price.

**Control tower > Parked events** (`EVENT_DEAD_LETTER_READ`) lists events whose
listener failed on every retry, filtered by status, event type and listener,
and shows one with its payload; `EVENT_DEAD_LETTER_MANAGE` can replay it or
discard it with a reason. A parked event cannot be made through the API, so
the browser specs cover the list, its filters and its gating; the backend's
own suites park, replay and discard real events.

## Webhooks

**Settings > Webhooks** (`WEBHOOK_READ`) lists the company's subscriptions and,
for one, its deliveries with status, attempts and the receiver's last answer.
`WEBHOOK_MANAGE` subscribes an address, edits or switches one off, rotates its
signing secret, sends a test ping and redelivers. The secret is shown once, in
the panel that issued it, and never again: the API does not return it. A help
panel shows the headers and how a receiver checks the signature.

The browser specs start a small HTTP receiver of their own, subscribe it and
check what the backend's delivery timer sends, signature included. That needs a
backend that accepts plain http to a private address, so start it with
`LMS_WEBHOOKS_ALLOW_HTTP=true LMS_WEBHOOKS_ALLOW_PRIVATE_TARGETS=true` when
running them locally; production keeps both off.

## Profile and settings

**My profile** (top bar, every signed-in person) shows who the platform says
you are (`GET /api/v1/me`) and edits your own preferences
(`/api/v1/settings/me`): theme, date format, time zone, rows per page, landing
page, and which events you want in the console or by e-mail (recorded only;
nothing sends them yet). `display.ts` applies the display ones: the theme on
`<html data-theme>`, the date format and time zone in the gateway's one
formatter, the page size of the record listings and the screen opened after
sign-in. The defaults are what the consoles did before, so a person who sets
nothing sees no change.

**Administration > Profile settings** (`SETTINGS_READ`; editing needs
`SETTINGS_MANAGE`) lists the company's setting profiles by scope, adds one for
the organisation, a unit, a customer or a vehicle with the usual pickers,
edits values with an input per setting type (a dated setting takes the day
its new version starts), shows each profile's versions and history, and
resolves what is in force for a unit, customer, vehicle and day, naming the
profile each value came from.

## Browser end-to-end tests

`e2e/` runs one set of specs against each console in Chromium, against a real
backend and database -- nothing is mocked. `.github/workflows/e2e.yml` does it
in CI. Locally, start Postgres and the backend with the demo tenant seeded
(`LMS_DEMO_SEED=true DEMO_ADMIN_PASSWORD=...`, and `CORS_ALLOWED_ORIGINS` set to
`http://localhost:4300`), then:

```
cd frontend
PAGES_BASE=/ API_URL=http://localhost:8080 bash build-site.sh
cd e2e && npm install && npx playwright install chromium
E2E_DEMO_PASSWORD=... npx playwright test
```

The demo tenant is shared by every spec, so a spec that defines a required
custom field retires it in a `finally`; a field left behind would fail every
later write to that kind of record.

One spec answers the delivery desk's three calls itself instead of reaching the
backend: recording a proof needs a consignment that a real trip has carried,
which the backend's own end-to-end suite builds and proves over HTTP. That spec
checks what the screen does with each answer. Likewise one maps spec answers a
trip's track and progress itself: a real reported track needs a dispatched trip
and a stream of positions. Everything else here is real, and map tiles are
always answered by the test.
Specs that need a consignment build one through the API (`newConsignment`), and
the partners they create are coded to sort last so they never push another
spec's partner off the first page of a list.

## Approvals

**Operations > Approvals** (permission `APPROVAL_READ`) is the one inbox for
every request waiting for a person to agree: an order's cancellation (when the
tenant switches approval on) and a proof of delivery's reversal. It opens on
what the caller can decide now; open a request to see what approving will do,
the policy it is decided under and its trail, then approve, reject with a
reason, or, as its requester, cancel it. The order desk's **Cancel order**
says "awaiting approval" when a request was raised instead, and the delivery
desk offers **Reverse proof** (permission `POD_REVERSE`) on a confirmed proof.
